# Walk animation

Status: complete.

## Context

On 2026-10-29 the user asked for a basic walk animation on rigged models to test how the skeleton moves, with the body type (animal, humanoid, or another creature that can have a skeleton) detected automatically and correctable by the user ("Que lo detecte").

What exists:

- UniRig writes a GLB with one skin whose bones are named `bone_0` … `bone_N`, with no semantic names, so legs and hips must be inferred from bone positions and hierarchy. A spike posed the space dog (`01M64AEQF3CZX1VAY4SBX5SVZQ`, 28 bones) this way: it found an arm bone above 55 % of the height, lateral and pointing outward, and leg bones below 55 % pointing down. The mesh deformed as expected, with one skinning spike at the hip that came from UniRig's weights.
- The engine's environment ships `bpy` 4.5. The export feature (`docs/userstories/export-formats/`) already runs bpy scripts from the client in a `QProcess` with `AppPaths.engine_python`, through `ModelConverter`.
- `Library.create_derived` makes a new entry from a source entry without touching the source; it is used for "add skeleton".
- The viewer (`viewer/viewer.js`, three.js) loads the GLB but does not play animations.

The walk is procedural: a looping cycle generated by code (leg swing, knee bend, counter-swinging arms, a small hip bob), stored as a glTF animation named `Walk`. It is meant to exercise the rig, not to be production animation.

Assumptions to confirm when approving:

- The animated model is saved as a new library entry named `<name> (walk)`, so the rigged original stays unchanged.
- Body types are `biped`, `quadruped`, and `unknown`. A walk exists for biped and quadruped. For `unknown` (no clear 2 or 4 legs: snakes, fish, odd shapes) the user must pick biped or quadruped, or cancel.

## US-01: Detect the body type of a rigged model

As a user, I want the app to tell whether my rigged model is a biped or a quadruped, so that it can pick a fitting walk without me knowing the skeleton.

Acceptance criteria:

- AC-01: A bpy script bundled with the client reads a rigged GLB and prints one JSON line with `body` (`biped`, `quadruped`, or `unknown`) and the bone names of each leg chain it found, root to tip. It uses no bone names, only rest-pose positions and hierarchy: the up axis is the model's tallest extent, and a leg is a chain whose tip ends near the lowest 10 % of the model and that starts below the upper part.
- AC-02: 2 legs means `biped`, 4 means `quadruped`, anything else `unknown`. A model with no skin reports an error instead.
- AC-03: The rigged space dog is detected as `biped`.

Dependencies: none.

Verification:

- `gpu`-marked tests (they need the engine environment, not a GPU): the space dog fixture gives `biped`. A synthetic quadruped built with bpy in the test (box body with 4 leg chains) gives `quadruped`. A synthetic chain with no legs gives `unknown`. The default unit run covers parsing the JSON and the error output (fake process).

## US-02: Add a walk animation as a new library entry

As a user, I want to add a walk cycle to a rigged model and correct the detected body type, so that I can see the skeleton move.

Acceptance criteria:

- AC-04: For a selected entry with a skeleton, an "Add walk animation" action runs detection first, then shows the detected type in a dialog. The user can keep it or switch between biped and quadruped, and can cancel. For `unknown`, nothing is preselected.
- AC-05: Confirming creates `<name> (walk)` as a derived library entry. Its `model.glb` holds the original mesh, skin and textures plus a looping glTF animation named `Walk`, about 1 s per cycle. Biped legs alternate. Quadruped legs move in a diagonal pair gait. Lateral chains above the legs, when found, counter-swing as arms.
- AC-06: The original entry is unchanged. A failed generation leaves no half-written entry, and the error is shown.
- AC-07: The action is disabled for entries without a skeleton and while another export or animation runs. New strings are translated in the Spanish catalog.

Dependencies: US-01.

Verification:

- `gpu`-marked test: the animated GLB re-imports in bpy with an action named `Walk` with keyframes on the leg bones. The leg tip moves forward and back over the cycle.
- Unit tests with fakes: dialog choices, derived entry naming, failure cleanup, enabled state.
- Manual: the walking space dog in the app viewer (US-03).

## US-03: Play animations in the viewer

As a user, I want the 3D viewer to play a model's animation, so that I can watch the walk without opening Blender.

Acceptance criteria:

- AC-08: When a loaded GLB has animations, the viewer plays the first one in a loop (three.js `AnimationMixer`). A play/pause control appears only for animated models.
- AC-09: Loading another model or clearing stops and disposes the previous mixer.
- AC-10: Exporting an animated entry to FBX keeps the animation, and GLB keeps it as a copy. README documents the walk feature and its limits (procedural, needs a skeleton, unnamed bones).

Dependencies: US-02 (manual check). The viewer code itself only needs any animated GLB.

Verification:

- `webengine`-marked test: loading an animated GLB fixture exposes the animation's name and advances its time.
- Unit test for the play/pause control state with the stub viewer.
- `gpu`-marked test: FBX export of the walk entry re-imports with an action.

Implementation runs as three lightweight hosted subagents (`haiku`) with separate files: the bpy script (`services/animate_rig.py`), the viewer (`viewer/viewer.js`, `index.html`), and the client action (`services/animator.py`, view model, library panel, main window). The script's contract (`detect` / `walk`, one `MODEL3D_RESULT {json}` stdout line) was fixed before they started. A spike on 2026-10-29 confirmed that a bpy action named `Walk` exports as glTF animation `Walk` and keeps the textures and skin.

Observed results (2026-10-29):

- `client/`: `uv run pytest` 240 passed, 16 deselected. `-m gpu tests/test_animate_rig_real.py tests/test_convert_real.py`: 12 passed (space dog detected as biped with chains bone_20..23 and bone_24..27; synthetic quadruped, no-legs and no-armature cases; walk keys bone_20/bone_24 and moves bone_23). `-m webengine tests/test_viewer_widget.py`: 2 passed (an animated `Spin` GLB plays, pause freezes time, the toggle hides for static models).
- Manual: `animate_rig.py walk` on the space dog gave `{"body":"biped","legs":2,"arms":2,"frames":24}`. Frames 0/6/12/18 rendered with bpy show alternating legs and counter-swinging arms. The FBX export of that file re-imports with a 24-frame `Walk` action (AC-10).
- AC-07: 11 new strings translated, `.qm` recompiled (173 finished, 0 unfinished). README documents the feature and its limits.
- Deviation: AC-04 says nothing is preselected for `unknown`; `QInputDialog.getItem` always selects one item, so the dialog says "Body type not detected" and starts on biped.
- Implementers: three `haiku` subagents with separate files, reviewed and integrated by the planner. They wrote tests together with code, so RED was not observed for the new tests. The planner changed the viewer's play/pause label to symbols (the page has no translation catalog).
- Not checked: the quadruped walk visually (only its exit code and leg count), and the full flow by hand in the running app.
